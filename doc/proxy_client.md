# 网络助手（GUI客户端） 需求规划

> Draft v0.6 | 2026-03-09

---

## 一、定位与架构

**网络助手**是运行在用户本地的独立 GUI 桌面程序，承担两类独立连接：

```
                     ┌── 节点管理（API）──────► VpsHelper 主控
网络助手（GUI）─────┤                                 │ Yamux 隧道
                     └── 代理流量（直连/链式）──► vpsprobe 探针 ──► 互联网
```

| 连接类型 | 通道 | 说明 |
|----------|------|------|
| 节点管理 | 网络助手 → 主控 API | 获取探针列表、节点状态、管理操作 |
| 代理流量 | 网络助手 → 探针（直连或链式） | 实际流量不经过主控 |

**链式代理**：可将多个探针串联（A → B → C），流量逐跳转发，实现多跳出站。

## 二、功能需求

### F1 — 主控连接

- 配置主控地址与登录凭据（支持多主控 profile）
- 从主控获取探针节点列表及状态（在线、延迟、代理是否开启）
- 通过主控下发节点管理指令（开启/关闭探针隧道端点服务）

### F2 — 代理模式

| 模式 | 说明 |
|------|------|
| 直连代理 | 网络助手直连单个探针代理出口 |
| 链式代理 | 多个探针串联，流量逐跳透明代理（A → B → … → 出站），跳数不限，每跳仅知道直接上下游 |

- 隧道通讯协议：AI Gateway 标准连接（对齐 Copilot 特征，详见 §七）
- 网络助手对外暴露本地 SOCKS5 / HTTP 代理端口供系统使用

### F3 — 本地代理接管

| 模式 | 说明 |
|------|------|
| 全局代理 | 所有流量走选定节点/代理组 |
| 规则分流 | 按规则匹配目标，映射到指定节点/代理组 |
| 直连模式 | 关闭代理，所有流量直连 |

- 一键设置/取消系统代理（HTTP / SOCKS5）
- TUN 模式（透明代理，首期实现）

#### 3.1 规则类型

| 规则类型 | 示例 | 说明 |
|----------|------|------|
| 域名精确匹配 | `example.com` | 完整域名匹配 |
| 域名通配符 | `*.google.com` | 子域名匹配 |
| IP 精确匹配 | `8.8.8.8` | 单个 IPv4/IPv6 地址 |
| CIDR | `192.168.0.0/16` | IP 段匹配 |
| GeoIP | `CN` | 基于 GeoIP 数据库的国家/地区匹配 |
| 最终规则 | `FINAL` | 上述均未命中时的兜底动作 |

#### 3.2 代理组（Proxy Group）

- 代理组是**一组节点的命名集合**，可包含单个探针节点或多跳链路。
- 规则的目标可以是：**具体节点名称** 或 **代理组名称**，统一称为「出口」。
- 内置特殊出口：`DIRECT`（直连）、`REJECT`（拒绝/屏蔽）。

#### 3.3 规则配置格式

每条规则由三部分组成：

```
<规则类型>,<匹配值>,<出口名称>
```

示例：

```
DOMAIN,api.openai.com,美国节点
DOMAIN-SUFFIX,google.com,香港组
IP-CIDR,8.8.8.0/24,美国节点
GEOIP,CN,DIRECT
FINAL,,全球组
```

#### 3.4 规则匹配优先级

规则按列表顺序**从上到下**依次匹配，第一条命中的规则生效，最后一条 `FINAL` 兜底。

#### 3.5 UI 交互

```
┌─ 规则列表 ──────────────────────────────────────────────────┐
│  [+ 添加规则]  [导入 Clash 节点]              [↑↓ 拖拽排序] │
├──────┬──────────────────────┬────────────────────────────────┤
│ 类型 │ 匹配值               │ 出口（节点/代理组）            │
├──────┼──────────────────────┼────────────────────────────────┤
│ 域名 │ *.google.com         │ 香港组                    [✎✕] │
│ CIDR │ 8.8.8.0/24           │ 美国节点                  [✎✕] │
│GeoIP │ CN                   │ DIRECT                    [✎✕] │
│FINAL │ —                    │ 全球组                    [✎✕] │
└──────┴──────────────────────┴────────────────────────────────┘
```

### F4 — 连通性测速

- 对节点发起延迟测速，按延迟排序
- 支持测速链式路径的整体延迟

### F5 — 流量统计

- 实时上行/下行速率、会话累计流量

### F6 — 系统托盘

- 后台驻留，托盘显示当前节点/链路与模式
- 右键快速切换

### F7 — 按进程查看连接/域名

在「连接」面板中，以**进程**为维度聚合所有活跃连接，方便用户精确追踪每个应用的网络行为。

#### 7.1 数据来源（进程–连接关联）

| 平台 | 方案 | 说明 |
|------|------|----- |
| Windows | `iphlpapi.dll` → `GetExtendedTcpTable` / `GetExtendedUdpTable` (含 PID 列) | 直接查询内核连接表，无需管理员权限（IPv4/IPv6） |
| macOS | `libproc` → `proc_pidinfo` + `PROC_PIDLISTFDS` | 枚举进程文件描述符，匹配 socket inode |
| Linux | 解析 `/proc/<pid>/net/tcp` 与 `/proc/<pid>/fd/` | 纯文件系统读取，无额外依赖 |

> **TUN 模式增强**：在 TUN 透明代理模式下，所有流量经内核网卡设备，可直接在驱动层拿到数据包的源 PID（Windows: WFP callout，macOS: Network Extension），无需轮询系统 API。

#### 7.2 数据项

每条连接记录包含：

| 字段 | 说明 |
|------|------|
| 进程名 | 可执行文件名，如 `chrome.exe` |
| PID | 系统进程 ID |
| 图标 | 从可执行文件提取（可选，仅桌面端） |
| 协议 | TCP / UDP |
| 本地地址:端口 | 客户端侧 |
| 目标地址:端口 | 远端 IP:Port |
| 目标域名 | 由 DNS 嗅探或 SOCKS5 CONNECT 的 hostname 字段还原 |
| 上行 / 下行 | 该连接已传输字节数 |
| 连接状态 | ESTABLISHED / TIME_WAIT / … |
| 建立时刻 | 时间戳 |

#### 7.3 DNS 域名还原

- **DNS 嗅探**：拦截本地 53 端口请求，建立 `IP → 域名` 映射表，用于将目标 IP 反查域名。
- **SOCKS5 hostname 直传**：若应用直接发送域名（不解析 IP），从 CONNECT 握手中提取。
- **HTTPS SNI**：解析 TLS ClientHello 的 SNI 字段，无需解密即可得到目标域名。

#### 7.4 UI 交互

```
┌─ 连接面板 ─────────────────────────────────────────────┐
│  [全部] [按进程]  搜索框  　　　  ↑↓ 速率  过滤▼       │
├─────────────────────────────────────────────────────────┤
│ ▼ 🌐 chrome.exe  (PID 1234)    ↑ 2.1 MB/s ↓ 8.4 MB/s  │
│   ├ www.google.com:443  TCP  ESTABLISHED  ↓ 3.2 MB     │
│   ├ api.example.com:443 TCP  ESTABLISHED  ↓ 1.8 MB     │
│   └ …                                                   │
│ ▼ 🔵 Telegram.exe (PID 5678)  ↑ 0.1 MB/s ↓ 0.5 MB/s  │
│   └ 149.154.167.92:443 TCP   ESTABLISHED  ↓ 0.5 MB     │
└─────────────────────────────────────────────────────────┘
```

- **分组折叠/展开**：点击进程行可展开/折叠属于该进程的所有连接。
- **右键菜单**（仅查看，暂不支持按进程屏蔽流量）：
  - 对单条连接：「断开连接」「追踪路由」
- **域名过滤**：支持通配符搜索，如 `*.google.com`。
- **排序**：按进程名、速率、连接数排序。

#### 7.5 采集频率与性能

| 参数 | 默认值 | 说明 |
|------|--------|------|
| 连接表轮询间隔 | 500 ms | 在 TUN 模式下可改为事件驱动，降低 CPU 占用 |
| DNS 映射表最大条目 | 5 000 | LRU 淘汰，避免内存膨胀 |
| 进程图标缓存 | 进程退出后保留 | 保证已关闭进程的历史记录仍可展示 |

#### 7.6 权限要求

| 平台 | 所需权限 |
|------|----------|
| Windows | 普通用户权限即可读取 `GetExtendedTcpTable`；TUN/WFP 驱动需管理员 |
| macOS | 普通用户可读 `proc_pidinfo`；Network Extension 需系统授权 |
| Linux | 普通用户可读 `/proc`；无额外要求 |

## 二附、链式代理设计（A → B → … → 出站）

### 跳数策略

- **跳数不设硬性上限**：用户可在客户端自由组合任意数量的探针节点，形成多跳链路。
- 实践中建议告知用户：跳数越多，累计延迟越高，请根据实际需要权衡。

### 逐跳透明代理（每跳仅知上下游）

每个探针节点在链路中**只感知直接的上游和下游**，对完整链路路径无感知：

```
网络助手  →  节点 A  →  节点 B  →  节点 C  →  目标服务

节点 A 只知：上游 = 网络助手，下游 = 节点 B
节点 B 只知：上游 = 节点 A，  下游 = 节点 C
节点 C 只知：上游 = 节点 B，  下游 = 目标服务
```

### 协议实现思路

链路由网络助手在本地负责**逐层建立**，推荐方式：

| 步骤 | 动作 |
|------|------|
| 1 | 客户端连接节点 A，发出 `CONNECT B:port` |
| 2 | 经由 A 的隧道，向 B 发出 `CONNECT C:port` |
| 3 | 经由 A→B 的隧道，向 C 发出 `CONNECT target:port` |
| N | 链路建立完毕，后续数据透传，各节点仅做 TCP 转发 |

这与 **SOCKS5 over SOCKS5**（洋葱拨号）等价，无需中间节点参与链路协商。

### 安全性说明

- 单个节点被攻击者控制时，攻击者**无法还原完整链路**，仅能知道来自哪个 IP、去往哪个 IP。
- 若需更强隐私保护，可在每跳之间叠加 TLS/加密隧道（后期扩展）。

## 三附、PKI 与通讯安全设计

### 总体策略

| 通道 | 安全方案 |
|------|----------|
| 网络助手 ↔ 探针（代理流量） | 私有 CA 签发证书，双向 TLS（mTLS）认证 |
| 网络助手 ↔ 主控 API | HTTPS + 独立 API Key（Bearer Token） |

### 私有 CA 流程

1. **主控生成根 CA**：首次初始化时在主控侧生成根 CA 密钥对与自签名证书。
2. **探针证书**：探针（vpsprobe）向主控申请，主控用根 CA 签发，证书中包含节点 ID/SAN。
3. **客户端证书**：网络助手首次连接主控后，由主控签发客户端证书，下发到本地。
4. **mTLS 握手**：网络助手与探针建立连接时双方出示证书，均验证对方证书是否由同一私有 CA 签发，防止中间人攻击。

### 主控 API Key

- API Key 独立于 Web 登录账号，在「系统设置」中生成/吊销。
- 网络助手在 HTTP Header 中携带：`Authorization: Bearer <api-key>`。
- API Key 仅用于管理面（节点列表、下发指令），不参与代理流量认证。

## 七、探针通讯隧道设计（AI Gateway 接入）

为了提升网络助手（NetHelper）与探针（vpsprobe）之间底层数据流的兼容性和安全性，双方的通讯通道**全面对齐 VS Code 与 GitHub Copilot API 之间的业界标准交互协议**。

本设计的详细通讯维度包括：
- HTTP/2 路由、Header 结构（如 `Copilot-Integration-Id`）对齐标准生态
- `Authorization` 认证机制（HMAC 安全握手，基于 `/v1/models` 端点）
- TLS 层深度协议一致性：包含 SNI 与 JA3/JA4 客户端握手特征（Chromium/Electron 引擎层面对齐）
- 依托 WebSocket 流的底层帧多路复用，支撑高并发的逻辑会话承载
